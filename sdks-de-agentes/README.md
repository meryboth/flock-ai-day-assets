# SDKs para construir agentes

A diferencia de `../orquestadores/` (frameworks pensados para coordinar *varios* agentes o pasos con estado), acá van los SDKs de base para programar un agente propio — ya resuelven el loop de tool-use y buena parte de la gestión de contexto (ver `../harness/`), así que lo que programás encima es la lógica específica de tu caso de uso: qué tools exponer, qué permisos darle (ver `../seguridad-agentes/`), y con qué modelo.

Todos resuelven lo mismo (recibir el pedido, decidir si llamar una tool, ejecutarla, devolverle el resultado al modelo, repetir), pero difieren en el nivel de abstracción, si son agnósticos de proveedor de modelo, y si traen soporte nativo para MCP (ver `../mcp/`) y multi-agente (ver `../coordinacion-multiagente/`) de fábrica.

- **[Claude Agent SDK](https://github.com/anthropics/claude-agent-sdk-typescript)** ([Python](https://github.com/anthropics/claude-agent-sdk-python), [docs](https://docs.claude.com/en/api/agent-sdk/overview)) — el mismo motor detrás de Claude Code, con tools de archivo/bash/búsqueda ya resueltas (Read, Write, Edit, Bash, Glob, Grep, WebSearch, WebFetch) y cliente MCP incorporado. El camino más directo si ya usás Claude Code y querés programar algo parecido.
- **[OpenAI Agents SDK](https://github.com/openai/openai-agents-python)** ([JS/TS](https://github.com/openai/openai-agents-js), [docs](https://openai.github.io/openai-agents-python/)) — liviano y agnóstico de proveedor (soporta 100+ modelos, no solo OpenAI). Sus dos conceptos distintivos: **handoffs** (un agente delega explícitamente en otro más especializado — un patrón de coordinación multiagente de primera clase, no algo que armás vos arriba) y **guardrails** (validación de inputs/outputs como parte del SDK, no un wrapper aparte).
- **[Google ADK (Agent Development Kit)](https://github.com/google/adk-python)** ([docs](https://github.com/google/adk-docs), también en Java/Go) — toolkit code-first de Google, optimizado para Gemini pero model-agnostic, con una UI web propia (`adk-web`) para debuggear el agente mientras lo armás — útil para ver el loop de tool-use paso a paso mientras aprendés.
- **[Vercel AI SDK](https://github.com/vercel/ai)** — el toolkit de TypeScript de los creadores de Next.js (la misma stack de esta plataforma de AI Day) para armar agentes y apps con IA con cualquier modelo. Buena opción si tu proyecto ya es un repo Next.js/React — el loop de tool-use se integra directo con React Server Components y streaming.
- **[Pydantic AI](https://github.com/pydantic/pydantic-ai)** ([docs](https://ai.pydantic.dev)) — el equivalente en Python, tipado de punta a punta (los errores de schema aparecen al escribir el código, no en runtime). Soporta prácticamente cualquier proveedor, incluido OpenRouter — relevante si tu agente necesita rutear entre modelos según costo (algo que no cubrimos todavía en este repo, pendiente).
- **[AWS Strands Agents](https://github.com/strands-agents)** — ya está en `../orquestadores/` porque también sirve para coordinar varios agentes, pero como SDK de base es igual de válido: enfoque model-driven, agnóstico de modelo y de nube.

## ¿Cuál elegir?

Si ya programás en TypeScript con Next.js, arrancá por Vercel AI SDK o Claude Agent SDK. Si tu stack es Python, Pydantic AI u OpenAI Agents SDK. Si ya estás en el ecosistema de AWS o Google Cloud, Strands o ADK respectivamente. Si tu caso de uso necesita que un agente le pase el control a otro de forma explícita (soporte → facturación, por ejemplo), el handoff nativo de OpenAI Agents SDK te ahorra tener que modelarlo vos mismo con un supervisor (ver `../coordinacion-multiagente/`).
